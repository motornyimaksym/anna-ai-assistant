# Unified assistant prompts

SPEC section 62 defines the current flow: S2 Assistant drafts every automatic client response, then S1 Handoff assesses the exact outgoing text and current conversation. No router, boolean approval, separate planner or server-authored booking messages remain.

The default Assistant prompt is short and brand-agnostic. It contains stable response behavior, not company facts, service boundaries or brand voice; those live in the file-backed Knowledge Base. Current enabled catalog data stays in each request and has priority for service fields. The file is capped at 3,000,000 UTF-8 bytes, stored privately, and indexed in OpenAI File Search. Admin Save/Reset activates a new vector store only after indexing succeeds. The model gets retrieved fragments, never the whole file. A token-protected static file URL uses a backend token rotated lazily after 24 hours, with a five-minute grace for its previous token.

Before each response, mandatory S2 guidance checks the three chat messages immediately before the current client message. It does not repeat facts the assistant already provided there, including price, duration, date/time or knowledge/catalog information; it answers new parts and may briefly note that a fact was already shared. A fact only stated by the client does not count as already answered. The assistant may repeat a fact on an explicit request to repeat or clarify it, and includes exact required facts in a new booking proposal. Bot Settings controls direct AI identity disclosure; it defaults on, while off allows a polite pivot but never a false claim of human identity. No relevant business match or ambiguous/conflicting KB passages go to a responder with a reason and no automatic reply. An explicit request for an unlisted, nonsexual custom service, or a request covered by the Knowledge Base's exact `Потрібна допомога людини` marker, also goes to a responder through terminal `request_human_assistance`; the default marker covers payment assistance, couple/four-hands requests, and training inquiries. Unlisted sexual acts remain outside scope. Service-specific voice and boundaries are business knowledge, not static prompt rules. After successful booking, its confirmation includes the configured address and ends with a brief warm welcome plus one friendly emoji. Server-side normalization replaces long dashes. Read-only tools provide service data, owned appointments and fresh schedule/Calendar evidence. For new bookings, `prepare_booking` stages a concrete proposal; after the client confirms the delivered proposal, `create_booking` writes the Calendar event with server-side identity, expiry and conflict checks. Uncertain writes go to human review. Humans handle cancellation and rescheduling. Legacy pending actions remain inactive.

Handoff returns a number from 0 to 1 for one condition: whether the outgoing reply sounds automated in context. It receives only the latest 20 delivered messages, including the incoming message, and the unsent draft. Copy-pasted wording can be natural and does not alone imply a bot. Score 1 always pauses; other scores pause only above threshold. Failures pause without sending a fallback message. Withheld drafts remain unsent.

New editable IDs are `assistant` and `handoff`, with independent new override documents. A one-time migration backs up the active legacy Assistant override, adds it to Knowledge Base as untrusted legacy text, indexes it, and resets the override only after indexing succeeds. The debug tester uses a synthetic recent conversation for Handoff and the active File Search store for Assistant without executing function tools.

Evaluation cases: disclosure on/off; no-match and ambiguous KB passages; service/catalog conflict; ordinary social turns; missing service/duration; dates supported only by fresh schedule and Calendar; robotic drafts; copied text; direct confirmation of a delivered appointment proposal; conditional agreement or changed details; stale source data; invalid provider output. Automated tests verify contracts and orchestration; model wording still requires qualitative evaluation.

Client-turn external API failures also enter the existing human queue. Responders receive only bounded, redacted service/status/code/message details, not raw provider bodies, credentials or prompts. Background schedule refresh stays best-effort.
