# Data model

## Calendar-only appointment cutover (SPEC §61)

Google Calendar events are the only live appointment records. New events carry private extended properties for version, booking/client/chat/service IDs, duration, price/currency, buffer, and creation time; event start/end contain appointment time. The description is readable context, not parsed for authoritative fields. Existing Firestore `bookings` and `bookingSlots` documents are a read-only migration archive after their Calendar events receive complete metadata. A legacy booking whose referenced Calendar event is missing is ignored as cancelled during cutover; no event is recreated or archive document changed. No booking flow reads or writes those collections after cutover. No booking lock or idempotency marker is added to Firestore. Calendar conflict checks include managed-event buffers; concurrent Calendar inserts can rarely overlap because Calendar offers no atomic time-range reservation.

Firestore collections are `services`, `availabilityRules`, `scheduleExceptions`, `telegramScheduleImports`, `clients`, `bookings`, `bookingSlots`, `conversations`, `telegramUpdates`, and `assistantSettings`. The shapes and meaning are defined by `SPEC.md`; shared Zod schemas in `packages/contracts` are the API representation.

The application uses the default Firestore Standard database. The backend Admin SDK is its only data client; Firestore rules deny direct client reads and writes. `services`, `availabilityRules`, `scheduleExceptions`, and `conversations` use their domain IDs as document IDs. Legacy `bookings` contain generated IDs, timing snapshots, and old lock references for migration inspection only. `telegramUpdates/{updateId}` records a claimed update ID.

`assistantSettings/prompt` stores a custom system prompt as `{ prompt, updatedAt }`. Its absence means the code default `ASSISTANT_SYSTEM_PROMPT` is active. Reset deletes the override document. Only the backend Admin SDK accesses this collection, via allowlisted admin API routes.

`assistantSettings/knowledgeBase` stores custom editable business context as `{ content, updatedAt }`, where content is a nonblank string of at most 12,000 characters. Its absence means the backend uses `DEFAULT_KNOWLEDGE_BASE` from `apps/api/src/default-knowledge-base.ts`; reset deletes the override and restores this repo default. A custom value replaces the default rather than appending to it. Only the backend Admin SDK accesses it through authenticated allowlisted routes. Each OpenAI system request concatenates the active prompt, editable knowledge base and a freshly rendered snapshot of enabled service names, descriptions, durations, prices and currencies from the booking catalog. That generated service section is not persisted, so it always reflects server booking facts. Knowledge-base content may include service eligibility conditions, such as prior-visit requirements; the assistant must apply these before recommending or booking. The knowledge base cannot override system rules or structured booking tools. No migration is needed.

`telegramScheduleImports/availability` stores `{ sourcePeerId, sourceChatTitle, sourceTopicId?, sourceTopicTitle?, slots, syncedAt, nextAttemptAt, calendarAvailability? }`. `slots` contains at most five `{ messageId, text, createdAt }` entries copied from the latest text messages in the selected Telegram chat or forum topic. `calendarAvailability` is backend-only and defined below. A missing topic ID means whole-chat history. The automatic sync claim updates `nextAttemptAt` transactionally, enforcing a five-minute minimum between incoming-message attempts across API instances. Settings manual refresh uses a transactionally leased retry run: failed transient attempts may bypass the automatic cooldown and retry up to five times with 10/20/30/40-second linear waits. A run lock prevents concurrent manual retries; success still starts the automatic cooldown. Admins can read the Telegram snapshot and request a throttled `/schedule` refresh; only owners can select a source. Imported entries have no edit/delete endpoint. Imported text is displayed verbatim on `/schedule`; booking availability still requires a live Calendar read. Firestore client rules deny direct access.

An owner-authorized configuration update may save the repository default text into this existing override document to activate it without deploying code. The document still represents an override (the UI shows Custom), even when the texts match. No schema change or migration is required. Reset uses the currently deployed code default, which may differ from an undeployed repository change.

`assistantSettings/behavior` stores bot timing overrides as `{ maxReadDelayMs, typingDelayPerSymbolMs, updatedAt }`. `maxReadDelayMs` is an integer from 0 through 3,540,000 ms (59 minutes); the admin UI displays this value in seconds and converts it to milliseconds for the existing API/storage field. `typingDelayPerSymbolMs` is an integer from 0 through 800 ms. If the document is absent, backend defaults are 2,000 ms and 600 ms respectively. Only the backend Admin SDK accesses this document, via the allowlisted admin API.

`assistantSettings/adminAccess` stores stakeholder administrator email grants as `{ emails, updatedAt }`, where `emails` is a list of at most 100 unique normalized lowercase addresses. A verified Firebase ID token whose email is in this list grants admin access; UIDs listed in `ADMIN_UIDS` are owners and retain access independently of the list. Owners alone may modify the email list. The backend Admin SDK is the only data client.

`services/{serviceId}` stores catalog fields (`name`, `description`, duration, buffer, price, currency, and enabled state) plus optional Telegram presentation fields: `photoUrl` (Firebase Storage download URL), `telegramCaption: { text, entities }`, and `telegramButtons` (API rows of `{ text, url }`). New services default to a 30-minute buffer in the admin editor and seed data; changing this default does not modify existing services. Firestore stores URL buttons as a flat array of `{ row, text, url }` records because Firestore does not support nested arrays; the repository groups them back into rows at the API boundary. The description remains assistant reference data. Caption entities use Telegram message-entity types with UTF-16 offsets. Photos are uploaded through the Admin API and stored in Firebase Storage; only backend code can write objects. Tokenized download URLs are public by design for Telegram delivery and catalog display.

Legacy `bookingSlots` uses `resourceId_yyyy-MM-dd_HH-mm` document IDs. Calendar-only code never acquires, reads, or releases these documents. `telegramUpdates/{updateId}` is an idempotency marker for Telegram updates, not appointment mutations.

Each archived `bookingSlots` document stores its legacy `bookingId`. The old transactional booking workflow is retired. A duplicate Telegram update is still rejected by atomically creating its update marker document.

No migration is needed for the initial schema. New persisted fields or collections require a prior specification and this document update.

## Service duration options

Services retain `durationMinutes` and `price` as their first option. Optional `durationOptions` stores up to nine additional `{ durationMinutes, price }` maps. All durations across the service must be unique (integer 15–480 minutes); prices are finite and nonnegative. Currency, buffer and Telegram content are shared. Missing options means the legacy single duration/price pair; no production migration is required. An option may be marked conditional in the editable knowledge base or service description for client-facing price-list presentation; it remains a selectable booking option when the client asks about that condition. The knowledge base can add business conditions but cannot override catalog prices or service IDs.

New Calendar events snapshot server-selected `durationMinutes`, `price`, `currency`, and `bufferMinutes` in private extended properties. Historical Firestore fields remain archive-only. Rescheduling preserves the Calendar snapshot, including when a catalog option is removed. Pending-action arguments may contain a numeric `durationMinutes` alongside existing string values. Availability and booking APIs use duration as the option selector, never trust a supplied price.


## Private assistant conversation state

`conversations/{chatId}/messages/{autoId}` stores `role` (`user`, `assistant`, or `human`), `text`, and ISO `createdAt`. Read the newest 20 by descending creation time, then reverse for model context. No raw provider payloads or credentials are persisted. An optional `activeHumanRequestId` on `conversations/{chatId}` pauses automation while its case is open or uncertain; it is independent of `assistantEnabled` and `humanTakeoverUntil`.

When Telegram reports `deleted_business_messages`, the backend deletes all stored message documents for that business chat and clears its summary, `openaiConversationId`, and pending action. Full-chat context reset is required because legacy message documents do not identify their Telegram message IDs. Booking and human-request documents are not deleted. This prevents later System One and System Two requests from reusing deleted chat context or approving an unseen proposal; it does not delete already submitted OpenAI provider records or historical owner-only diagnostic payloads.

The protected Conversations-page `Clear context` action uses the same context reset. It preserves bookings, assistant-enabled state, manual takeover, and active human-request references. Its response reports the number of removed message documents. Provider-side records and owner-only diagnostic payloads remain under their separate retention controls.

`assistantSettings/humanAssistance` stores `{ thresholdPercent, usernames, updatedAt }`. `thresholdPercent` is an integer from 0 through 100 (default 60); `usernames` is a unique list of at most 20 normalized lowercase Telegram names without `@` (default empty). Missing document uses both defaults. The list controls who may enroll and act; it does not provide a Telegram DM address. A separate `humanResponders/{telegramUserId}` record stores the verified numeric user ID, private `chatId`, observed normalized username, and `enrolledAt`. Authorization also checks the current configured username on every command; removal or username change invalidates the record. Only the backend Admin SDK reads these records.

`humanRequests/{requestId}` stores `conversationId`, `telegramChatId`, optional `businessConnectionId`, initiating `telegramUpdateId`, `status` (`open`, `sending`, `uncertain`, `answered`, `released`), `reason` (including legacy `knowledge_gap` and `jev_unavailable` values, plus current human-assistance reasons), optional probability, threshold snapshot, original question and later queued client text, timestamps, optional answer actor, and per-responder notification delivery status. New cases have no client acknowledgment; historical `acknowledgement` values remain readable. Historical cases retain their reason/probability fields for compatibility; no new Jev-routing cases are created. Read-only booking planner clarification/failure does not open a case. The request ID is server-generated; a transaction enforces at most one active case per conversation and prevents duplicate cases for an update. Case send claims use unique lease IDs and expiries; completion checks lease ownership. Confirmed human delivery closes the case and adds a `human` conversation message unless newer client text arrived during send; that case reopens, retaining `lastAnswer` for admin review. Explicit rejection reopens it; uncertain delivery stays paused for admin reconciliation and is never automatically resent. Notification state similarly prevents duplicate fanout under Telegram uncertainty. The Admin API supplies open-case views without exposing other clients' data to responders. Data is retained under existing protected Firestore access rules; routine logs exclude questions, answers, and tokens. No migration of existing conversations is required.

Conversation documents optionally contain `pendingAction`: `{name, arguments, expiresAt}`. Name is `create_booking`, `cancel_booking`, or `reschedule_booking`; arguments contain only service/time or booking/time fields. Expiry is an ISO timestamp. System One natural-language approval consumes this field before execution. A new proposal summary must have been sent and saved in assistant message history before the client can approve it; identity is always supplied from the current Telegram message. Old documents without this field remain valid. Existing booking documents and slot transactions are unchanged.

## Telegram user account connection

`telegramAccount/primary` is backend-only (existing deny-all rules). Stores `phase` (`disconnected`, `code`, `password`, `connected`), `ownerUid` for pending flow, `expiresAt` (epoch ms), `attempts`, `retryAt` (Telegram flood cooldown, epoch ms), `startRetryAt` (code-request cooldown, epoch ms), masked phone, optional username, and `encrypted` AES-256-GCM envelope `{ version: 1, iv, tag, ciphertext }`. The encrypted JSON contains only `{ session, phone?, phoneCodeHash? }`. Code and 2FA password are never stored. Associated data binds ciphertext to `telegramAccount/primary:v1`. A random Secret Manager key protects pending and connected sessions. Do not rotate/delete the key while a session is connected: disconnect first.

`leaseId` and `leaseUntil` serialize network mutations using Firestore transactions. Completion checks the same unexpired lease before saving; stale workers cannot overwrite newer state. Leases expire after 50 seconds; individual Telegram operations time out after 20 seconds. Empty/disconnected records can retain cooldown metadata; completed logout removes session and identity fields. Pending authorization is usable only for ten minutes and by the initiating owner.

## Media Store

`media/{id}` stores server-generated `id`, `description`, `debounceSeconds` (integer 0-31,536,000; default 86,400), `enabled`, `kind` (photo/video), `filename`, `contentType`, `sizeBytes`, `url`, `storagePath`, `createdAt`, `updatedAt`. Files live under `media/{id}/{uuid}.{jpg,png,mp4}` in the default Storage bucket. No client-provided URLs or paths are accepted. Public tokenized download URLs are intended for Telegram/client sharing; rules continue to deny direct client writes. Replace/delete cleans up superseded objects best-effort. Service data is retained separately for booking and is not automatically migrated.

`conversations/{chatId}/mediaDeliveries/{mediaId}` stores optional `lastSentAt` (epoch ms), `leaseId`, `leaseUntil` (epoch ms). A transaction reads the current media item and delivery record, enforces per-item cooldown, then writes a 60-second exclusive lease. Completion checks lease ownership before recording success/uncertainty and releasing it. Explicit rejection only releases the lease. Metadata edits/file replacements preserve history. Deleting an item can leave its small delivery records; IDs are never reused. The assistant receives eligibility metadata, never raw Storage paths, and the server remains authoritative at send time. No index or migration is required.

## Private AI workspace

`aiChatUsers/{uid}/threads/{uuid}` is backend-only and isolated from booking conversations. Each document stores `id`, `title`, ISO `createdAt`/`updatedAt`, at most 40 `{ role: user|assistant, text, createdAt }` messages (6,000 characters each), optional `action`, and optional `leaseId`/`leaseUntil`. The action stores UUID, `send_message|reply_to_message`, numeric peer ID, resolved title, exact body, optional reply message ID, expiry, status (`pending|sending|sent|cancelled|uncertain`), and a backend-only SHA-256 session fingerprint. The authenticated UID always selects the parent path; callers cannot supply an owner. List newest 50 by `updatedAt` (single-field index). Transactions claim turns and consume proposals before external effects. Stale leases cannot overwrite later turns; interrupted sends are displayed as uncertain and never replayed. No plaintext sessions, raw MCP results, or OpenAI credentials are persisted here. Existing Firestore deny-all client rules apply.

Schedule import diagnostics add `status`, ISO `lastAttemptAt`, and an internal random `attemptId` to `telegramScheduleImports/availability`. `nextAttemptAt` remains epoch milliseconds and is exposed as ISO time; `syncedAt` is last success. Automatic and manual claims update attempt identity/status/time transactionally. Completion writes only if the claim still matches. Source selection replaces source ID/title, clears slots/syncedAt/status, removes the attempt identity, and preserves cooldown/last-attempt time, preventing an old request from overwriting a newly selected source. Public responses omit attempt identity. Missing diagnostic fields default to idle (or success for existing snapshots).

New source selections and successful imports normalize `sourceChatTitle` to the first nonblank trimmed Telegram title or name, capped at 255 characters, or `Telegram chat <peer ID>` when unnamed. Peer IDs remain authoritative. No schema change or migration is required.

## Google Calendar connection

`googleCalendarAccount/primary` stores a backend-only managed connection: `phase`, `revision` UUID, optional `email`, `calendarId`, `calendarTitle`, `checkedAt`, AES-GCM `encryptedToken`, top-level `expiresAt` (epoch milliseconds), and pending `{ ownerUid, stateHash, encryptedProof }`. Pending proof contains PKCE verifier and ID-token nonce. A callback consumes pending state atomically and uses the captured revision to commit; disconnect/new authorization invalidate old revisions. No token exists in public status. A disconnected document is retained to override legacy environment configuration. Single-document transactions serialize lifecycle updates. Existing deny-all client rules apply. The separate encryption key is in Secret Manager and must be preserved across releases.

Bookings gain optional `googleCalendarId` alongside `googleCalendarEventId` so later changes to the selected calendar cannot route event updates/deletions to the wrong calendar. Legacy records without it use the active selection. No event migration occurs when changing selection or reconnecting.

Schedule sources optionally store `sourceTopicId` (positive 32-bit integer) and `sourceTopicTitle` (1–255 characters, verified by Telegram). The source identity is `(sourcePeerId, sourceTopicId?)`; absent topic fields mean whole-chat history, requiring no migration. Claims carry the topic ID and successful snapshots refresh its verified title. Selecting a different topic clears old snapshots and invalidates the attempt identity, preserving cooldown. Whole-chat selection removes both topic fields. A missing topic never falls back to parent history.

Settings manual retry coordination uses internal `manualRetryRunId` and `manualRetryUntil` fields on the existing availability document. They serialize a user-triggered retry batch, expire after crashes, and are omitted from public responses. The batch has at most five attempts, retries only transient statuses, and uses 10/20/30/40-second waits. No migration is needed.


## Raw schedule context and booking recovery (section 47)

`telegramScheduleImports/availability` keeps the five recent source messages and import diagnostics. It also stores backend-only `calendarAvailability`: `{ status: 'ready', checkedAt, rangeStart, rangeEnd, busy }` or `{ status: 'unavailable', checkedAt }`. `busy` holds at most 500 `{ start, end }` intervals from the selected conflict calendars for the next 30 days, with no event titles or attendees. A successful Telegram import replaces this Calendar snapshot; a failed Calendar read records `unavailable` rather than retaining old busy data. Source changes clear it. Old documents without this field remain readable. Public schedule responses omit it. The assistant receives raw message text and timestamps as reference data; booking plans still fetch Calendar live. New writes omit derived `availability`, parser version, covered dates, and schedule revision. Historical derived fields are ignored. A failed Telegram refresh preserves the last preview for admins but does not provide valid assistant schedule context.

`googleCalendarAccount/primary` adds `grantedScopes: string[]` and `conflictCalendarIds: string[]` (destination included). Missing grant metadata is unknown, not permission denial. Legacy records remain readable; check/reconnect fills metadata.

Bookings add optional public `calendarOperation` (create/reschedule/cancel) and internal `operation` containing immutable ID, kind, original/target times, all held slot keys, lease ID/expiry and safe status. Creation writes booking and operation with locks in one transaction. Reschedule retains both sets of locks until success; cancellation retains locks until deletion is verified. Original calendar/event IDs are persisted before Google mutations. Existing `calendarSyncStatus` surfaces pending/failed/synced. No new client Firestore access; Admin SDK only. Recovery endpoints require admin authorization. Human requests add `operation_error` and `uncertain` reasons; existing queue/delivery model remains unchanged.

## Booking planner and diagnostics

`assistantSettings/bookingPrompt` stores `{ prompt, updatedAt }` with the same 20,000-character, nonblank validation as the conversation prompt. Absence selects `BOOKING_SYSTEM_PROMPT`; reset deletes only this override. The structured booking plan is validated in memory and is not stored as an alternative booking model. Only a ready creation/reschedule plan becomes an existing `conversations/{chatId}.pendingAction`; natural-language approval and durable Calendar operations apply.

Diagnostics retain the latest 200 typed entries globally, with UUID, timestamp, trace, anonymized chat reference, stage, severity and bounded details. The legacy `assistantDiagnostics/recent.events` array migrates on write to the index and individual event documents described in section 60 below. Request previews may include sanitized prompt/context and response content; credentials and hidden reasoning are excluded. Backend-only access; the read API requires the single selected owner UID, not ordinary administrator privileges.

## System One / System Two

`assistantSettings/prompt` applies to System Two General; `assistantSettings/bookingPrompt` continues to control the structured planner inside System Two Booking. Additional optional documents for System One and Booking conversation overrides are defined below; no migration is required. The existing diagnostic shape records routing as `assistant_started` with `intent: general|booking`, `reason: system_one_selected`; no raw selector inputs or provider results are stored.

## Natural-language proposal confirmation (section 50)

`conversations/{chatId}.pendingAction` gains optional `id` (UUID) and `confirmationText` (nonempty string, maximum 4,000 characters). Every new proposal writes both; the text is the exact displayed summary, including action, appointment details and confirmation invitation. Existing documents remain readable without migration. Natural approval requires both fields; legacy proposals without summaries cannot use natural approval and must be replaced with a fresh proposal; client chat has no command shortcut.

Compare-and-consume transactions verify the complete expected action and current client/automation/human state, then delete only `pendingAction` and update `updatedAt`. A valid false approval decision clears only a matching snapshot. Telegram activity uses a field-only timestamp update to preserve concurrent changes. Reply delivery checks positive Telegram `ok: true` before recording the proposal summary in history. No boolean result or probability is persisted as booking authorization, and no new collection/index is added. Existing deny-all client access remains unchanged.

`aiChatUsers/{uid}/threads/{uuid}.openaiConversationId` and `conversations/{chatId}.openaiConversationId` are optional OpenAI Conversations API IDs. Legacy documents acquire one on their next conversational model request. IDs stay scoped to the authenticated UID/thread or Telegram chat/client. Firestore messages serve UI, routing, confirmations, planning and audit, not conversational Responses input.

`assistantSettings/systemOneApprovalPrompt`, `assistantSettings/systemOneProbabilityPrompt`, and `assistantSettings/bookingConversationPrompt` store optional `{ prompt, updatedAt }` overrides for their respective `/prompt` tabs. `assistantSettings/prompt` and `assistantSettings/bookingPrompt` remain the General and Booking planner overrides. Missing documents select code defaults. Only backend Admin SDK accesses these documents; saving one prompt never changes another.

Routing overrides now store `{ instructions, general, booking, updatedAt }` in `assistantSettings/systemOneRoutingPrompt`. Legacy `{ prompt, updatedAt }` documents remain readable: `prompt` becomes instructions, while `general` and `booking` use defaults. Reset deletes the routing document. Other prompt override documents retain `{ prompt, updatedAt }`.

All editable prompt fields allow 1–20,000 nonblank characters, covering the shipped General default. Knowledge-base limits remain separate.

### Browser admin appearance preference

`localStorage['massage-admin-theme']` optionally holds `light` or `dark` for the booking admin, standalone AI workspace and their login screens. It contains no account or business data, is not sent to the API, and creates no Firestore document. Missing, invalid or unreadable values default to `dark`.

Telegram `openaiConversationId` may be replaced transactionally after a specific first-request missing-tool-output rejection. Replacement compares the rejected ID, client identity and automation/human-pause state. No new fields; all proposals, human cases and booking operation state remain intact. Recovery seeds only the same chat/client's bounded recent messages; ordinary turns still send only the new message.

### System One provider setting

Backend-only `assistantSettings/systemOne` stores `provider` (`openai` or `typesafe`) and ISO `updatedAt`. A missing document means `openai`; no migration. Protected admin GET/PUT exposes only `provider`. Each System One decision reads it once. Existing deny-all client rules apply. No tokens or prompt content are stored here.

Outgoing Probability checks reuse `assistantSettings/humanAssistance.thresholdPercent`. `humanRequests.reason` additionally accepts `bot_detectability` (with validated probability) and `probability_unavailable` (without score). The existing bounded `question` field carries labeled client-question and unsent-draft excerpts; no withheld draft is appended to delivered message history. Notification chat links are resolved transiently; no new fields, collections or indexes.

### Detailed request diagnostics (section 60)

`assistantDiagnostics/recent` becomes `{ ids: string[] }`, a transactional oldest-first index of at most 200 UUIDs. `assistantDiagnostics/{uuid}` stores one bounded DebugEvent with request metadata; each serialized Firestore record is capped at 32 KiB. Complete sanitized request and response bodies are stored as private Cloud Storage objects under `assistant-diagnostics/{uuid}/request.json` and `response.json`; Firestore records contain no body text or public URLs. The owner-only no-store payload endpoint verifies the diagnostic event is retained before loading either object. Append atomically publishes the event and index; eviction removes event documents transactionally and deletes associated objects afterward. The owner-only Clear action transactionally empties the index and removes retained event documents, then best-effort deletes their body objects; events written after that transaction remain retained. On first write, legacy `recent.events` are copied into retained event documents and the old array removed; legacy reads remain supported before migration. Existing records keep their captured preview and truncation status. No credentials or hidden reasoning; full sanitized request bodies may include client/prompt data and stay restricted to the exact debug owner. Existing deny-all Firestore client rules apply.
