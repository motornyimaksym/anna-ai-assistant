03 · Послідовність

05 · Час

Звідки береться доступність

Telegram user accountВибраний чат або topic: до 5 останніх текстів розкладу.
+
Google CalendarЖиві busy-інтервали вибраних conflict calendars.
→
get_booking_contextСтан джерел, timestamps, часовий горизонт; без назв приватних подій.

Оновлення розкладу

Вхідний update запускає імпорт, але Firestore claim обмежує читання раз на 5 хвилин. Адмін може запускати refresh з контрольованими retries.

Рішення щодо часу

Повідомлення про розклад описують окремі початки, а не безперервні вікна. Весь сеанс + buffer має не перетинати busy-інтервали.

Stale / недоступне джерело не означає вільний час. Перед фактичним створенням BookingService знову читає Calendar.

SPEC.md §62; apps/api/src/booking-context.service.ts; apps/api/src/telegram-schedule-import.service.ts

06 · State machine

Створення запису

Тільки новий запис · дві різні репліки клієнта
1. ВибірПослуга + тривалість + час із чату.
→
2. prepare_bookingКаталог, час, schedule, Calendar, buffer → незмінні факти proposal із TTL.
→
3. Доставка proposalПриродне формулювання; сервер перевіряє послугу, тривалість, дату/час, ціну, валюту й код.
→
4. Наступне «так»Явне підтвердження → create_booking без model-selected деталей.
Сервер перевіряєТой самий client/chat; дійсний proposal; остання доставлена відповідь містить точні факти без суперечливих чисел/валют; atomic consume; свіжий conflict check; перевірений Calendar event.
Стоп-умовиНеявна згода, прострочення, змінений proposal, конфлікт часу або невідомий результат Calendar → без фальшивого підтвердження, передача людині.

07 · Джерело істини

Google Calendar як сховище записів

Що зберігає подія

Стабільний app event ID.
Private extended properties: booking/client/chat IDs, service, duration, price, buffer.
Людинозрозумілий опис для власника календаря.

Алгоритм конфлікту

Зчитати вибрані conflict calendars.
Порівняти інтервал [start, end + buffer) з busy.
Створити event; перевірити запис і повторно перевірити конфлікти.
Calendar не має атомарного «перевірити й вставити» для довільного інтервалу. Рідкісні паралельні накладки можливі; виявлені випадки передаються людині.
Firestore bookings і bookingSlots — архів міграції, не live state. Скасування й перенесення — людські дії в поточному S2 flow.

SPEC.md §61–62; apps/api/src/calendar.ts; apps/api/src/booking.service.ts

08 · Алгоритм

S1: чи звучить відповідь як бот?

ВхідОстанні 20 повідомлень + точний недоставлений draft.
→
estimateProbabilityОдна умова, число p ∈ [0,1]. Копіпаста сама по собі не ознака бота.
→
ПорігНалаштування thresholdPercent; суворе p×100 > threshold.
Допуститиp < 1 і p×100 ≤ threshold → Telegram send.
Передати людиніВищий score, рівно 1 за будь-якого порогу, помилка або oversized input → draft приховано.
Provider: OpenAI за замовчуванням або TypeSafe → fallback OpenAI. Строгий формат результату; timeout і output-budget recovery.

10 · Control plane

Адмінпанель і конфігурація

Firebase Sign-in → ID token → AdminGuard API.
Firestore: каталог, knowledge base, S2/S1 prompts, provider, handoff threshold, conversations.
Calendar OAuth: окреме підключення, вибір destination та conflict calendars.
Schedule: джерело Telegram-розкладу, стан імпорту, busy preview.
Media Store: метадані Firestore, об’єкти Storage, cooldown і Telegram delivery.
Debug: лише designated owner; metadata у Firestore, повні sanitized payloads у private Storage.
UI доступ не замінює серверну авторизацію. Власник керує окремими чутливими налаштуваннями; debug має ще вужчий доступ.

12 · Trust boundaries

Дані й межі довіри

Calendar
Живі appointments, busy intervals, private ownership metadata. Жодного нового live booking у Firestore.
Firestore
Чати, pending proposal, claims, catalog, prompts, settings, human cases, diagnostic metadata.
Cloud Storage
Медіа та приватні повні sanitized debug request/response bodies.
Secrets / tokens
Secret Manager для provider/bot keys; шифровані Calendar і Telegram sessions; API перевіряє auth і webhook secret.
Модель
Отримує лише дозволений контекст; tool allowlist і перевірки прав виконуються в коді.
